# CRM-360 — Unified Customer Profile (SPEC-W20 Agent A)

Enterprise app `crm-360`: one screen per customer — the base contact
record plus a read-only aggregation over the tenant's bookings, helpdesk
tickets, field-service work orders and loyalty wallet, with agent notes
(pinnable), normalized tags, and a merged chronological timeline.

- Backend: `services/booking-service/internal/crm360/` (self-contained
  package per the W20 anti-collision contract; exposes `RegisterRoutes` +
  `NewStore`/`DialStore`)
- UI: `apps/admin-web/app/app/[orgSlug]/apps/crm-360/` (search + list,
  `contacts/[contactId]` profile page) + shared components in
  `apps/admin-web/components/apps/crm-360/`
- Entitlement (integrator): appgate `app_id = "crm-360"` on the whole
  `/v1/crm` route group; perms — `view_analytics` for GET,
  `manage_bookings` for POST/PATCH/DELETE (the W19 `requireReadWrite`
  chain, verbatim)

## 1. Data model

The package owns exactly two write-side tables, both tenant-scoped with
`ENABLE` + `FORCE ROW LEVEL SECURITY` and the `tenant_isolation` policy
(`tenant_id = current_setting('app.tenant_id')`), bootstrapped
idempotently by `Store.ensureSchema` (devices/W19 idiom, pg_policies-
guarded). Every tenant query runs inside `withTenant` (`SET LOCAL
app.tenant_id`).

### crm_notes

| Column | Type | Notes |
| --- | --- | --- |
| `id` | uuid PK | `gen_random_uuid()` |
| `tenant_id` | uuid | |
| `contact_id` | uuid | the contact the note is on |
| `author` | text | staff identity (JWT sub via `Deps.UserFromContext`; falls back to the request body's `author`, then `''`) |
| `body` | text | 1–8000 bytes after trim |
| `pinned` | bool | default false; pinned notes sort first |
| `created_at` / `updated_at` | timestamptz | `updated_at` stamped on PATCH |

Index: `(tenant_id, contact_id, pinned DESC, created_at DESC)`.

### crm_tags

| Column | Type | Notes |
| --- | --- | --- |
| `tenant_id` | uuid | part of PK |
| `contact_id` | uuid | part of PK |
| `tag` | text | part of PK; lowercase, 1–40 chars, `[a-z0-9-_]` |
| `created_at` | timestamptz | |

`PRIMARY KEY (tenant_id, contact_id, tag)` makes tag adds naturally
idempotent (`ON CONFLICT DO NOTHING`). Index `(tenant_id, tag)` backs the
search tag filter. Max 50 tags per contact.

### The 360 aggregation (read-only)

The 360 view JOINS the existing domain tables — it never writes to them
and creates no copies. Source tables (discovered from the W13–W19 stores
and `infra/postgres/init-scripts`):

| Section | Source | Degrades? |
| --- | --- | --- |
| contact record | `contacts` (+ W12 `source`/`external_id` columns) | **required** — missing contact → 404 |
| tags | `crm_tags` (own table) | always present |
| open ticket count + latest 5 | `tickets` (helpdesk, W19) | empty when table absent |
| recent bookings (latest 5 by `starts_at`) | `bookings` (W1) | empty when table absent |
| active work orders | `work_orders` (field-service, W19; statuses `created/assigned/en_route/on_site`) | empty when table absent |
| loyalty wallet `{balance, tier}` | `loyalty_wallets` (W19) | `null` when table absent or no wallet row |
| consent status | identity-service `consents` (separate DB) | `null` unless `Deps.ConsentResolver` is wired |

Every optional source is guarded by an
`information_schema.tables`-existence check **per query**, so a booking
DB where an app is not yet deployed answers an empty section — the 360
endpoint NEVER 500s on a missing optional source (SPEC-W20 contract).

### Timeline (merged feed)

`{ts, kind, summary, ref_id}`, newest first, merged across:

| kind | Source | One item per… |
| --- | --- | --- |
| `booking` | `bookings.created_at` | booking (summary carries status + scheduled start) |
| `ticket_event` | `ticket_events` joined to `tickets` by `contact_id` | helpdesk event (created/assigned/status_changed/note/first_response/resolved/reopened) |
| `work_order` | `work_orders.created_at` (+ `completed_at`) | work order creation, plus a completion item when `completed_at` is set |
| `loyalty` | `loyalty_ledger` (`beneficiary_id` = contact id, per `internal/loyalty/ledger.go`) | points movement (debit → `-N pts`, credit → `+N pts`) |
| `note` | `crm_notes.created_at` | note (body preview truncated to 120 bytes) |

Limit: `?limit=` default 50, max 200 (each source contributes up to
`limit` rows pre-merge; the merged feed is capped at `limit`).

## 2. Endpoints (`/v1/crm`)

All routes require the `X-Tenant-Slug` header (the package resolves the
tenant itself via `Deps.Resolver`, mirroring the workorders idiom).
Mounted by `crm360.RegisterRoutes` on the ROOT router.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/v1/crm/contacts/search?q=&tag=&limit=` | name/phone/email **prefix** search + optional tag filter (default limit 20, max 100) |
| GET | `/v1/crm/contacts/{id}/360` | unified profile (404 unknown contact) |
| GET | `/v1/crm/contacts/{id}/timeline?limit=` | merged feed (default 50, max 200) |
| GET | `/v1/crm/contacts/{id}/tags` | list tags |
| POST | `/v1/crm/contacts/{id}/tags` | add tag `{tag}` — normalized lowercase, validated; idempotent replay → 200 (no duplicate event) |
| DELETE | `/v1/crm/contacts/{id}/tags/{tag}` | remove tag (404 when not attached) |
| GET | `/v1/crm/contacts/{id}/notes` | list notes (pinned first, then newest) |
| POST | `/v1/crm/contacts/{id}/notes` | add note `{body, pinned?, author?}` → 201 |
| PATCH | `/v1/crm/notes/{id}` | edit body and/or toggle pin `{body?, pinned?}` |

### curl examples

```sh
# Search (prefix semantics: "ada" matches "Ada Lovelace"; "lovelace" does not)
curl -H "X-Tenant-Slug: acme" \
  "https://api.example.com/v1/crm/contacts/search?q=ada&tag=vip&limit=20"

# 360 profile
curl -H "X-Tenant-Slug: acme" \
  "https://api.example.com/v1/crm/contacts/$CONTACT_ID/360"

# Timeline
curl -H "X-Tenant-Slug: acme" \
  "https://api.example.com/v1/crm/contacts/$CONTACT_ID/timeline?limit=50"

# Tags
curl -X POST -H "X-Tenant-Slug: acme" -H "Content-Type: application/json" \
  -d '{"tag":"vip"}' \
  "https://api.example.com/v1/crm/contacts/$CONTACT_ID/tags"
curl -X DELETE -H "X-Tenant-Slug: acme" \
  "https://api.example.com/v1/crm/contacts/$CONTACT_ID/tags/vip"

# Notes
curl -X POST -H "X-Tenant-Slug: acme" -H "Content-Type: application/json" \
  -d '{"body":"Customer prefers morning calls","pinned":true}' \
  "https://api.example.com/v1/crm/contacts/$CONTACT_ID/notes"
curl -X PATCH -H "X-Tenant-Slug: acme" -H "Content-Type: application/json" \
  -d '{"pinned":false,"body":"Customer prefers afternoon calls"}' \
  "https://api.example.com/v1/crm/notes/$NOTE_ID"
```

Validation failures → 400 (`ErrInvalidInput`); unknown/cross-tenant
contact/note/tag → 404; bad UUID path params → 400.

## 3. Events (CloudEvents via the transactional outbox)

Topic `opendesk.crm.events.v1` (SPEC-W20 contract §5), emitted
best-effort post-commit (empty topic = graceful no-op). Note bodies are
deliberately NOT in the payloads — events stay small and free-text stays
off the bus; consumers fetch via the API.

| Type | Fires when | data |
| --- | --- | --- |
| `com.opendesk.crm.NoteCreated` | POST note | `{tenant_id, note_id, contact_id, author, pinned, ts}` |
| `com.opendesk.crm.NoteUpdated` | PATCH note (edit or pin toggle) | same shape (resulting state) |
| `com.opendesk.crm.TagAdded` | tag newly attached (NOT on idempotent replay) | `{tenant_id, contact_id, tag, ts}` |
| `com.opendesk.crm.TagRemoved` | tag detached | same shape |

## 4. Metering — explicitly NONE

crm-360 emits **no** usage metering (SPEC-W20 contract §4: "crm-360 and
workforce: NO metering (internal-ops apps)"). Notes, tags and profile
reads are internal-ops productivity actions on data the tenant already
owns; there is no billable customer-facing action to price. Adding
`crm_note_created`-style rows to `opendesk.usage.events` would be pure
noise for billing. This decision is also recorded in the package doc
comment (`internal/crm360/crm360.go`).

## 5. Entitlement & config (for the integrator)

- **appgate app_id:** `crm-360` — gate the whole `/v1/crm` group.
- **Perms:** GET/HEAD → `view_analytics`; POST/PATCH/DELETE →
  `manage_bookings` (reuse the W19 `requireReadWrite()` chain verbatim).
- **Tenant:** the package self-resolves `X-Tenant-Slug` via
  `Deps.Resolver` (bookingops.TenantResolver satisfies the interface) —
  wire exactly like workorders; httpapi's `tenantMiddleware` may run
  ahead in the chain as in the W19 wiring.
- **Config envs** (all optional — the app is fully functional with zero
  config):

  | Env | Default | Purpose |
  | --- | --- | --- |
  | `CRM360_EVENTS_TOPIC` | `opendesk.crm.events.v1` | lifecycle-events topic; empty disables event emission |

- **Deps seams:** `Store` (`crm360.DialStore(ctx, databaseURL)`),
  `Resolver`, `Logger`, `CRMEventsTopic` (from the env above),
  `UserFromContext` (JWT sub → note author; the httpapi `userFrom`
  accessor), `ConsentResolver` (optional — see §6).

## 6. Limitations & follow-ups

- **Conversations are not joined.** The `conversations` table lives in
  the separate conversation database (`03-conversation-schema.sql`) and
  carries no `contact_id` key — a per-contact conversation lookup is not
  resolvable from the booking DB in this wave. Follow-up: add a
  contact-linkage key to conversations or a cross-service read, then add
  a `conversations` profile section + timeline kind.
- **Consent status is `null` by default.** Consent records live in
  identity-service's `consents` table (separate DB, keyed by
  `data_subject_id` + `purpose`, not contact UUID). The package exposes
  the optional `Deps.ConsentResolver` hook; a resolver error degrades to
  `null` (logged), never to a failed profile. Follow-up: integrator
  wires an HTTP resolver against identity-service once a
  contact→data-subject mapping exists.
- **Work-order intermediate status changes are not on the timeline** —
  the booking DB keeps no work-order history table, only `created_at` /
  `completed_at`. The `opendesk.fsm.events.v1` stream has the full
  transitions if a follow-up wants to persist them.
- **Search is prefix-only** (`ILIKE 'q%'` on name/email, `LIKE` on
  phone) — deliberately predictable and index-friendly; fuzzy search is
  an OpenSearch concern (see `infra/opensearch`).
- **Timeline is a read-time merge** (no materialized feed) — fine at
  operator QPS; a high-traffic portal surface would want a materialized
  per-contact feed.
